# RefCard05 – Full-Stack auf AWS (ECR, ECS, RDS, S3)

## Bewertete Lernaufgabe

### Ausgangslage

Sie nutzen CI/CD von GitHub, die GitHub Actions um das Projekt nach einem Commit und Push automatisiert zu builden, testen und als Image auf Docker-Hub abzuspeichern.

Sie haben in RefCard03 ein eigenständiges Spring-Boot-Backend mit MariaDB aufgesetzt. In dieser Lernaufgabe führen Sie Frontend (React + Vite), Backend (Spring Boot) und Datenbank (MariaDB) als vollständige Fullstack-Anwendung auf AWS zusammen: Die Datenbank läuft neu auf Amazon RDS, der Bilder-Storage auf Amazon S3 statt auf einem lokalen Volume.

Frontend und Backend bleiben in getrennten Repositories mit je eigener GitHub-Actions-Pipeline, eigenem Image in Amazon ECR und eigenem Service in Amazon ECS – analog zum Muster aus RefCard02/03, neu mit zwei unabhängigen Services statt einem. Das Frontend wird als nginx-Container in ECS ausgeliefert (gleiches Muster wie bisher, keine neue Auslieferungsart).

**Wichtig:** Sie arbeiten mit einem AWS-Academy-Learner-Lab-Account. Eigene IAM-Rollen und OIDC funktionieren dort nicht. Nutzen Sie stattdessen die von AWS Academy pro Sitzung bereitgestellten temporären Zugangsdaten als GitHub Secrets (siehe Aufgabe 3).

## Aufgabe 1: Zwei Repos – CI/CD für Frontend und Backend

**Aufgabe:**

- Nutzen Sie Ihre bestehenden Repositories aus RefCard03 (Frontend) und RefCard03/04 (Backend).
- Jedes Repo behält seine eigene GitHub-Actions-Pipeline: build → test → Image nach Amazon ECR pushen.
- Frontend: eigenes ECR-Repository, Image enthält den fertigen Vite-Build hinter einem nginx.
- Backend: eigenes ECR-Repository, Multi-Stage-Dockerfile (Maven/Gradle-Build → schlankes JRE-Image).
- Versionieren Sie beide Images strukturiert mit Git-Tags (Fortsetzung aus RefCard03) – der Tag beeinflusst die Image-Bezeichnung in ECR.
- Setzen Sie im Frontend-Repo `VITE_API_BASE_URL` auf die URL des Backend-Service.

## Aufgabe 2: Backend an RDS (MariaDB) und S3 anbinden

**Aufgabe:**

- Erstellen Sie eine MariaDB-Instanz auf Amazon RDS (in einer im Learner Lab freigegebenen Region, z. B. us-east-1 oder us-west-2).
- Konfigurieren Sie das Spring-Boot-Backend so, dass es die Verbindungsdaten (Host, Port, DB-Name, User, Passwort) aus Umgebungsvariablen/Secrets bezieht – keine Zugangsdaten im Code.
- Übernehmen Sie den Bilder-Storage-Endpoint aus RefCard04 und stellen Sie ihn auf einen Amazon-S3-Bucket um statt auf ein lokales Volume.
- Erstellen Sie eine IAM-Rolle mit Zugriff ausschliesslich auf den konkreten S3-Bucket (Least Privilege) und binden Sie diese an den Backend-Task.

## Aufgabe 3: Deployment auf ECS – zwei Services, Learner-Lab-Zugangsdaten

**Aufgabe:**

- Deployen Sie Frontend und Backend als zwei unabhängige ECS-Services (Fargate); das Frontend läuft als nginx-Container.
- Stellen Sie sicher, dass eine Änderung am Image für beide Services automatisch zu einem neuen Task/Container in ECS führt (Redeploy).
- Learner Lab: `iam:CreateRole` und OIDC funktionieren nicht. Hinterlegen Sie stattdessen die im „AWS Details"-Panel bereitgestellten temporären Zugangsdaten (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`) als GitHub Secrets und verwenden Sie diese in `aws-actions/configure-aws-credentials` (`aws-access-key-id` / `aws-secret-access-key` / `aws-session-token` statt `role-to-assume`).

**Achtung:** Diese Tokens laufen mit der Lab-Session ab. Beschreiben Sie in Ihrer Dokumentation, wie Sie damit umgehen (Secrets bei neuer Session aktualisieren).

**Hinweis:** In einem produktiven AWS-Account wäre OIDC (wie in EX-03 gezeigt) der Best-Practice-Ansatz – halten Sie diesen Vergleich kurz in Ihrer Doku fest.

## Aufgabe 4: Lokale Entwicklung zusammenführen

**Aufgabe:**

- Da Frontend und Backend in getrennten Repos liegen: Richten Sie eine Möglichkeit ein, beide lokal zusammen laufen zu lassen (Docker Compose), z. B. ein eigenes, kleines Compose-Verzeichnis, das die (lokal gebauten oder von ECR gezogenen) Images beider Services referenziert.
- Dokumentieren Sie kurz, wie ein Teammitglied das gesamte System (Frontend, Backend, Datenbank) lokal startet.

## Ergebnis festhalten

- Halten Sie Ihr Vorgehen je Repo (oder in einem gemeinsamen Markdown) fest: kurz, knapp, verständlich.
- Ergänzen Sie Screenshots, die Ihr Ergebnis zeigen (Commits, Workflows, ECR, ECS, S3-Bucket, RDS-Instanz). Achten Sie darauf, dass Ihre individuelle Lösung eindeutig erkennbar ist.
- Reichen Sie die Links zu beiden Repos (Frontend, Backend) sowie ggf. zum Compose-Verzeichnis ein.
